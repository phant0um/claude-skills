## Themes

### 1. Interaction Flow Transformation (Grilling $\rightarrow$ Questionnaire Loop)
The primary behavioral change is how the skill engages with the user. We are deprecating unstructured grilling in favor of a structured, sequential questionnaire loop. This enforces better reasoning by forcing the user to resolve one specific ambiguity at a time rather than being bombarded with options. The focus is now on providing recommendations that guide decisions (recommending answers), which sharpens the quality of the interaction.

### 2. Architectural Decoupling and Canonicalization
To stabilize the skill definition, complex knowledge regarding decision models (`model-per-step`) has been separated into an internal `wiring vault`. The canonical version of the skill is now defined as lean, utilizes Fable for unknowns mapping, and relies on strong lineage tracking. This ensures the primary module remains focused purely on the interaction mechanism, while decision logic is stored separately, improving maintainability and preventing configuration drift (split-brain reconciliation).

### 3. Enhanced Gatekeeping and Anti-Self-Grilling
We have introduced mechanisms to prevent common pitfalls: a `Facts vs Decisions` framework explicitly tells the model when it should solve (Facts, done internally) versus when it should query the user (Decisions). Crucially, a **Confirmation Gate** ensures that sessions do not terminate with an action plan—a user must explicitly confirm understanding before implementation is allowed.

## Watch out

### Behavior Changes for Users
*   **No More Open Grilling:** Expect the skill to guide you step-by-step using structured questions and recommendations, rather than allowing open-ended questioning or arbitrary lists of options.
*   **Mandatory Confirmation:** Any plan generated by the system will **not execute** until you explicitly confirm your understanding ("ok, pode agir"). Failing to confirm means the session halts at the decision point.
*   **Self-Grilling is Disabled:** The model is now strictly prohibited from exploring code/context and asking questions about its own perceived knowledge (Facts) unless that involves a critical architectural Decision posed to the user.

### Technical Gotchas
*   **Context Dependency is Key:** The system relies heavily on extracting context (codebase, notes) to formulate insightful questions. If context is sparse, expect the loop to be less performant or generalize more broadly.
*   **Decision Tree Rigidity:** The new execution flow follows a strict, defined Decision Tree (Problem $\rightarrow$ Scope $\rightarrow$ Approach $\rightarrow$ Evidence). Understanding what options are presented will dictate the effectiveness of your response.
